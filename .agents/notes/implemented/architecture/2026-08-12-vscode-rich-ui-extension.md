# Agent Note: dsh-vscode — the rich-UI VS Code panel

Status: implemented

English | [中文](2026-08-12-vscode-rich-ui-extension.zh.md)

> Scope: a new product assembly `apps/vscode` (workspace name `dsh-vscode` — unscoped because `vsce` rejects a scoped extension `name`; the `deepseek-ai` publisher makes the extension id `deepseek-ai.dsh-vscode`) that hosts the full DeepSeek Harness Web GUI inside a VS Code webview panel — one managed `dsh web` per window, the complete dsh client stack bundled statically into the webview, and a postMessage↔fetch bridge across the extension-host boundary. This note covers the panel/server/bridge foundation; editor-side native integrations land in later phases.

> Relationship to the community `dsh-external/dsh-vscode`: that extension is a native VS Code Chat Participant (`@dsh`) that deliberately ships no trajectory page and no embedded Web UI. This assembly occupies the opposite point — it keeps the rich GUI (Plan Mode, trajectory, slot-based tool cards, settings) by hosting the real client stack. The two are complementary and share only the `dsh web` server contract.

## Problem

The Web GUI is the product's richest surface, and the desktop shell already proved a client shell can own a `dsh web` server's lifecycle. VS Code users want that GUI beside their editor, with editor-native affordances layered on later. A webview is a browser, so the GUI can run there unchanged in principle — but two facts block a naive port. First, a webview's page origin is `vscode-webview://…`, which the server's `/api` browser-trust fence refuses (the fence demands a loopback Host or a same-origin `Origin`; DNS-rebinding defense is the whole point). Second, a webview's CSP forbids fetching plugin bundles from the server, so the client module system's default fetch-a-bundle-per-plugin loading cannot run.

## Decision

**The extension host owns the server and proxies every `/api` byte; the webview never touches the network.** `ServerRuntime` (`apps/vscode/src/runtime.ts`) spawns `dsh web --host 127.0.0.1 --port 0` through the shared `@deepseek-ai/dsh-web-launcher` primitive — the same resolution/readiness/HTTP-poll logic the desktop shell uses, extracted into `packages/util/web-launcher` in the same body of work — and tree-kills it through `@deepseek-ai/dsh-process-tree` on deactivate. The webview's transport is a new `PostMessageApiClient` (`packages/client/connection`, a third platform subclass beside Web and Fixture) that posts each request over the embedder port; `ApiBridge` (`apps/vscode/src/bridge.ts`) replays it against the server's loopback origin, and confines every request to that origin under the `/api/` prefix (`resolveApiTarget`) — a webview can run injected script, and the host holds loopback network reach the page must not borrow for other targets (absolute URLs, protocol-relative or backslash authorities, non-API paths are refused before any fetch). A loopback Host passes the fence like any non-browser client, so nothing about the fence changes — the bridge is the reason the GUI reaches the server at all, and it reports `isLoopback: true` because the extension host's fetch, not the webview page, is the wire client. The bridge and both host-side wire clients resolve the origin through a live getter, never a captured server instance, so the restart command swaps the `ServerRuntime` and every consumer follows to the new port (the webview reconnects through the same bridge).

**The GUI is bundled statically and booted through the unchanged shell kernel.** `AppWebEntry` gained one seam — a `staticPlugins` map registered through the module system's existing `registerStatic` path — so the webview can hand it every plugin implementation at build time instead of a fetch graph. `webview/vite.config.ts` bundles the roster (the `dshClient` rows of `apps/cli/config/web.cordis.yml` minus dev-only hmr, plus a VS Code theme adapter) into one asset pair served through `asWebviewUri` under a strict CSP (`script-src` pinned to the extension's asset origin, no inline scripts). The theme adapter maps the editor's `--vscode-*` variables onto the client's `--dsw-alias-*` tokens through the existing `ThemeService.register()`, so the GUI follows the editor's color theme.

**Two constraints the browser shell never meets make this bundle different from `apps/web`'s, and both render a blank panel when violated.** A *library* build (`build.lib`, which the webview needs to emit one named asset pair) does not substitute `process.env.NODE_ENV`, because Vite assumes a library gets bundled again downstream; nothing bundles this one further, so React's CJS entry throws `process is not defined` at module top level unless `define` supplies it. And the panel CSP carries no `'unsafe-eval'`, while the vendored loader builds its `!!js` evaluator with `new Function` at module top level — `webview/loader-config-utils-stub.ts` replaces that module (resolved by path, since `vendor/loader` reaches it relatively) with an evaluator that throws instead of existing, which is correct here: the webview boots from a static roster and boot graph, so no `!!js` node can reach it. `font-src` additionally allows `data:` because the single stylesheet inlines its webfonts. Zod's optional JIT probe still trips one recoverable CSP violation on the console; it falls back to interpreting and validation stays correct.

**The window is the isolation unit.** One `ServerRuntime` per window (`--port 0` guarantees no collision between windows or with a standalone `dsh web`); the first workspace folder is the server cwd, so the harness adopts it as the default project root. The panel starts the server in the background and never blocks on it — the webview's own connection loop reconnects when the server becomes ready.

## Alternatives considered

- **VS Code Chat Participant (the community `dsh-vscode` route)** — native and light, but the Chat API cannot express the rich GUI (trajectory, Plan Mode, slot tool cards); that extension states the omission outright. Rejected here precisely because the rich GUI is this assembly's reason to exist.
- **Webview fetches the server directly** — impossible: the `vscode-webview://` origin fails the `/api` trust fence, and relaxing the fence for it would reopen the DNS-rebinding hole the fence closes.
- **Fetch plugin bundles at runtime (the browser shell's default)** — the webview CSP forbids remote script and inline execution; a static single bundle is the CSP-clean shape, and it also removes the server round-trips the browser shell pays at boot.
- **Add `'unsafe-eval'` to the panel CSP** — the one-line way past the loader's top-level `new Function`, and rejected for the same reason the bridge confines its request targets: the webview is treated as capable of running injected script, so handing it string-to-code execution to save a stub module is the wrong trade.
- **Reuse the desktop Electron shell inside VS Code** — VS Code is its own Electron host; a nested shell cannot mount. The reusable part is the launcher, which is why it moved to a shared package rather than being copied.

## Consequences

The launcher extraction made `apps/desktop` a consumer of `@deepseek-ai/dsh-web-launcher` (its inline `launcher.ts` and unit suite moved wholesale into the new package). The `PostMessageApiClient`, the `AppWebEntry` static-plugins seam, and the theme adapter are covered keyless: the transport's unary/SSE/abort/cleanup behavior in `packages/client/connection/tests/webview-bridge.spec.ts`, the platform selection in `client-apply.spec.ts`. The extension host's own logic is keyless-tested over injected spawn/fetch/kill seams (`apps/vscode/tests/runtime.spec.ts` including dispose aborting an in-flight readiness poll, `bridge.spec.ts` including the SSRF-escape refusals, `panel.spec.ts`), and `roster.spec.ts` fails the build if the static roster drifts from the shipped web config. None of those can see a bundle that downloads and then throws, which is why `apps/vscode/tests/webview-boot.e2e.ts` joins the browser lane (`vitest.web.config.ts`): it serves the real `dist/webview` output through the real `panelHtml()` document — the shipped CSP included — and fails unless React mounts with no uncaught error. That single assertion pins both constraints above; a unit suite cannot substitute for it, because the failure mode is a bundle that loads perfectly and renders nothing. Booting the panel inside a real editor stays a manual step until a `@vscode/test-electron` lane lands. Until the packaging phase bundles a server closure, the extension depends on the launcher resolving a `dsh` (DSH_BIN, a checkout, or PATH); a machine with none gets a start error in the panel rather than a broken GUI.
