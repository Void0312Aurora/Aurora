# Agent Note: 真实可执行文件契约测试采用套件级超时

Status: implemented

[English](2026-08-08-executable-contract-suite-timeouts.md) | 中文

## Problem

`scripts/oxlint-contract.spec.ts` 断言的是 Oxlint 可执行文件的真实行为：每个用例写入一个探针文件，针对一份把 `ignorePatterns` 清空的配置启动真正的 `oxlint` 二进制，再对其诊断输出做断言。清空忽略列表是必需的——仓库配置忽略 `**/oxlint-contract-*`，否则探针会被跳过——而这会让每个用例都对整个工作区构建一份类型感知程序。

这项工作很慢，更关键的是耗时波动极大。同一次调用、断言同一件事，在某台开发机上实测介于 13s 到 49s 之间，而 CI 对同批用例报告的是 1.5s 到 6.5s。因此 Vitest 默认的 5s 超时是按宿主机速度与负载判定失败的，而非按产品行为；在报告里这种失败与真实回归无法区分。

该文件六个用例中有三个带独立的 `20_000` 超时，另外三个停留在默认值。正是这种形态掩盖了问题：`reports an unused suppression` 在 CI 上以 5s 默认值失败而其姊妹用例通过，看起来像是单个用例不稳定，而不是整个文件的预算从未设定。随后只提高那一个用例，失败就转移到另外两个——其中一个本就是 `20_000`——因为六个用例并发运行会抬高每个用例的资源竞争。

## Decision

超时是这个套件的属性，在其 `describe` 上声明一次：

```ts ignore-check
describe('Oxlint executable contract', { timeout: 90_000 }, () => {
```

三处逐用例的 `20_000` 被移除；套件预算覆盖每个用例，包括后续新增的用例。放在套件而非逐用例上正是要点：新用例无法再静默继承 5s 默认值，而失败用例恰恰就是这样产生的。

预算按最坏观测值取值，而非中位数。按中位数取值会把宿主机波动转化为间歇性红灯，其消耗的评审注意力高于宽松上限消耗的挂钟时间——通过的用例永远不会等到它的截止时间，因此上限只在真正挂死时才付出代价。

这条适用于会针对整个工作区启动真实可执行文件的套件，并非普遍抬高超时的许可：进程内的慢测试是应当修复的测试，而 90s 上限只是延后暴露的挂死仍然是缺陷。

## Alternatives considered

**保留逐用例超时并补上缺失的那些。** 这是最先尝试的做法，且失败了：提高被报告的那一个用例后，失败转移到两个姊妹用例，其中一个已经是 `20_000`。逐用例取值还需要在每次新增用例时重新审计，而该文件已经漂移到一半用例无保护的混合状态。

**让探针更廉价，使 5s 默认值够用。** 成本来自工作区范围的类型感知程序，而它正是被测对象——项目发现的契约测试无法在不削弱断言的前提下缩小其程序。把配置的 `ignorePatterns` 限制到某个子树的方案经过实测，结果反而更慢。

**把套件标记为 flaky 并重试。** 重试是掩盖信号而非修复：这里没有任何非确定性，且重试一个 49s 的套件比在正确上限下跑一次代价更高。

**将该套件从覆盖率门禁中排除。** 它已经是覆盖率豁免的（`scripts/coverage-exempt.ts`）；豁免控制的是插桩而非超时，聚合门禁仍会原样运行它，失败依旧存在。

## Consequences

该文件的时序契约集中在一处，新用例自动继承。此套件中真正的挂死现在需要每用例最多 90s 才会显现，而非 5s；接受这一点，是因为另一种选择是间歇性失败——其定位成本高于等待成本。

预算背后的测量数据依赖具体宿主机，在源码注释中以观测区间的形式记录，而不作为推导新预算的规则。其他套件保留各自的超时；本 Agent Note 并未设定仓库级默认值，90s 这个数字也不是可以不经测量就照搬的先例。
